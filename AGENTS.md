> 5. **AUTOMATIC SPEC VERSION BUMP, SOFT APPROVAL RESET, LAST-APPROVED SNAPSHOT, ORPHAN PURGE, CLEAN SLATE DRAFT & AUDIT REPORTING RULE (STORAGE-FIRST)**: Whenever creating new files, editing, updating, or deleting/refactoring the content of a specification item `💎 K...`, the Agent MUST strictly follow the Storage-First Sequence: (1) **Mandatory Disk Storage Re-Read & Targeted Content Update (Universal Multi-User Soft-Reset & Cold History Snapshot)**: Before modifying any `.md` files, the Agent MUST explicitly re-read (`view_file`) the target storage file `.qmd/usa/<fileId>/a2u.json` directly from disk to capture the freshest real-time approval states (`item.x === "y"`) clicked by the User on the Obsidian UI. The Agent MUST ONLY target the specific Canonical Base-36 ID keys `💎 K...` whose content was actually edited in the turn. In `.qmd/usa/.../a2u.json`, every key maps to an array `Array<ScopeItem>` `[ { c, s, x, r, v, w } ]` (where `w` is the Base-36 approval timestamp `Date.now().toString(36)`, and `r` is an optional micro-reason string $\le 256$ characters, omitted when empty). Cold History Snapshot in `.qmd/shr/<fileId>/his.json` and Soft-Reset in `a2u.json` are ONLY triggered when an item was PREVIOUSLY APPROVED by at least one user (including author `a2u`, where `item.x === "y"` or `item.x === true`). For each such previously approved item, the Agent MUST preserve the last approved snapshot into the Cold Audit store `.qmd/shr/<fileId>/his.json` under `his[kid][oldVer] = { t: oldText, ts: timestamp, u: user, r?: reason }` and record the new version `his[kid][newVer] = { t: newText, ts: timestamp, u: user, r?: reason }` before updating to the new version `item.v = newBase36Ver`, updating `item.w = Date.now().toString(36)` and soft-resetting `item.x = null` in `.qmd/usa/.../a2u.json` (`null` or `"!"` to trigger the Outdated Comet badge `☄️` on Obsidian UI, distinct from human rejection `x = false` / `"n"` / `❌`, NEVER setting `x = "?"` for previously approved items, NEVER storing `t`, `lh`, or `u` inside `ScopeItem` in `a2u.json` / `<user>.json`, NEVER setting named properties directly on the array object instance and NEVER soft-resetting untouched keys); (2) **New File Creation & Clean Slate Rule (Quy chuẩn Kho Rỗng Khi Tạo Mới Tài Liệu / Thêm Mục Mới & Miễn Trừ Soạn Nháp Chưa Duyệt)**: When creating a new `.md` file, the Agent MUST initialize `.qmd/usa/<fileId>/a2u.json` with an empty object `{ "v": 3, "a": {} }`. When additively generating fresh `💎 K...` keys into existing documents, or editing items that have NEVER been approved by any user (`item.x === "y"` is absent), the Agent MUST apply the Unapproved Exemption: update text directly in `.md` without taking snapshots in `his.json`, without bumping `v`, and without writing unapproved keys into `.qmd/usa/<fileId>/a2u.json` (as writing `x: null` or `x: false` would erroneously trigger the Outdated Comet badge `☄️` or Rejection `❌` instead of the pure Pending Question Mark `❓`). All fresh unapproved items MUST remain absent from storage until explicitly approved by the User (via UI click or `💎 K... .` / `💎 Kstart ... 💎 Kend`); (3) **Content Deletion / Orphan Purge**: When deleting, condensing, or removing specification items/blocks from the Markdown (`.md`) file, the Agent MUST immediately purge all orphaned Canonical Base-36 ID keys from `.qmd/usa/.../a2u.json` (and corresponding records in `.qmd/shr/.../his.json` if applicable) to prevent garbage key accumulation and maintain 1:1 integrity with the document; (4) **Markdown Layer Cleanliness & Immutable Presentation**: In the `.md` file, update the specification text cleanly without altering existing Base-36 Primary Keys `qc("c", "💎 K...", "<icon-type>")`. All version snapshots and outdated states are handled 100% in the storage layer (`.qmd/usa/` for Hot State `{ c, s, x, r, v, w }` and `.qmd/shr/` for Cold Audit) without adding redundant `"❓"` or `"💎 V..."` parameters to Markdown; (5) **Mandatory Soft-Reset & Storage Audit Reporting**: In every turn where any `💎 K...` content was edited, updated, or soft-reset, the Agent MUST include a dedicated **Storage & Soft-Reset Audit Table** in the final response detailing for each modified ID: ID code, Prior State (`"y"` / `false` / `"?"`), Snapshot History in `his.json` preserved (`v` & `t`), Post State Storage (`null` / `false` / `"?"`), UI Display (`☄️` / `❌` / `❓`), and New Version Base-36 (`💎 V...`).

> 17. **MANDATORY SPEC UX, SUB-HEADING & API SPECIFICATION STANDARDS**:
>     - **Two-Layer Identity Architecture**: Machine/AI layer is permanently grounded by immutable Base-36 ID keys (`💎 K...`) in DataviewJS `qc("c")` buttons and versioning in `.qmd/usa/.../a2u.json`. The Human/Readability layer (Sub-headings `###`, `####`) MUST NOT redundantly repeat top-level file prefixes (e.g. use `#### 3.1.1. 💎 POST-SYNC-PAYLOAD`, `#### 3.1.2. 💎 POST-SYNC-RESULT`, `#### 3.2.1. 💎 GET-QUERY-PARAMS`, `#### 3.2.2. 💎 GET-QUERY-RESULT`). This maximizes Outline reading UX and clean Wikilinks (`[[File#Heading|...]]`).
>     - **Collapsible Details Badges (`CHI TIẾT [Xem ⯆]`)**: Approval buttons inside collapsible `<details><summary>` blocks in tables MUST use the Eye semantic icon `"👁️"`: `$= qc("c", "💎 K...", "👁️") [Xem ⯆]`.
>     - **Code Block Title & Caption Conventions**: All code blocks MUST have an emoji prefix in titles (e.g. `title="📄 filename.json"`). JSON payload/response captions MUST use the Payload Package icon `"📦"` (`$= qc("c", "💎 K...", "📦") *Mẫu Payload...*`), while table captions use Chart `"📊"`.
>     - **Data Contract vs URL Query Parameters**: POST Data Contract tables label the column as `BẮT BUỘC` (representing API & Business data integrity requirements). GET URL Query tables MUST NOT have a redundant single `BẮT BUỘC` column (as query params are conditional filter combinations); use a clean 4-column layout (`STT | THAM SỐ | MÔ TẢ | CHI TIẾT`), place Primary Key (`id` / `cust_id`) on Row `01`, and note `(tất cả tham số đều là kiểu string)` in the heading description, place Primary Key (`cust_id`) on Row `01`, and note `LIKE` search support for query strings (e.g. `string (phone)`).
>     - **URL Query Parameter Completeness Principle (Nguyên tắc Đối xứng Tham số Tra cứu)**: Tham số `keyword` hỗ trợ tìm kiếm đa trường trên những thuộc tính nghiệp vụ nào (`code`, `phone`, `email`, `name`, `address`), thì API bắt buộc phải cung cấp đầy đủ các tham số lọc đơn lẻ tương ứng đó trong bảng tham số URL Query.
>     - **Technical PK vs Business Code Separation**: Always clearly separate technical primary keys (`cust_id` / `Id` GUID) from business display codes (`code` / `Code` `DRV1-32825`).
>     - **Twin Term + Tooltip Dual Anchor Standard (Quy chuẩn Duyệt kép Thuật ngữ & Chú giải qc("t") / cặp mảng)**: Khi định nghĩa thuộc tính trong bảng cấu hình/schema/API hoặc thuật ngữ chuyên môn trong câu văn có cấu trúc gồm `[Tên nhãn nghiệp vụ ngắn gọn]` đi kèm `[Diễn giải chi tiết/Các giá trị hợp lệ]`, Agent **BẮT BUỘC** sử dụng cú pháp duyệt kép `$= qc("t", ["💎 Kterm", "💎 Ktip"], ["dia", "tip"], ["Nhãn hiển thị", "Diễn giải chi tiết"])` thay vì viết văn bản tĩnh dài dòng. Cú pháp này thiết lập 2 điểm thẩm định độc lập qua cặp mảng `["vế thuật ngữ", "vế chú giải"]` (Nút 1 đầu duyệt thuật ngữ, Nút 2 đuôi duyệt diễn giải). Khi rê chuột vào văn bản thuật ngữ, Obsidian hiển thị Tooltip Flyout tương tác có nút `[📋 Copy Text]` và `[📋 Copy Tip]`; khi rê chuột vào 2 nút emoji chỉ hiển thị thẻ thẩm định kỹ thuật chuẩn (Spec Card) mà không lặp lại nội dung diễn giải.
>     - **Tooltip Block, Twin Pair & Closing Hole Standard (`ttb` / `["term", "tip"]` / `🕳️`)**: Whenever creating block containers (`qc("a")`) with supplementary terminology/English keywords, use the twin pair array `["Text", "Tooltip"]` (`$= qc("a", "💎 K...", "ttb", ["Text Hiển Thị", "Tooltip Giải Nghĩa"])`) instead of putting parentheses `()` in the title. Inner content inside block cards MUST be formatted as natural prose sentences without redundant nested `**Key**: Value` prefixes. Every block container `qc("a")` MUST be closed with the Hole emoji `🕳️` and repeat the Block ID: `🕳️`$= qc("z", "💎 K...")``. NEVER omit the `🕳️` prefix or the ID in `qc("z")`.
>     - **Atomic String Sanitization Breakdown**: Inside `Sanitization` blocks, individual cleanup operations (1. Invisible/control char filtering; 2. Leading/trailing `trim`; 3. Internal whitespace collapsing / casing) MUST be split into separate atomic lines with their own Base-36 IDs for 1:1 QA verification.
>     - **Validation Error Field Binding**: Validation rules MUST explicitly specify the target field name (e.g. `... cho field "name"` or `kèm field: "name"`) for precise Backend DTO mapping and automated QA test assertions.
>     - **Atomic Validation Breakdown**: Validation rules across different contexts (Insert vs Update/Partial Update) or independent checks (Required, Format, Length) MUST be split into separate atomic lines with independent Base-36 ID buttons for 1:1 QA verification. Never combine multiple conditions into a single long sentence.
>     - **Partial Update Sub-bullets Hierarchy**: In Upsert/Sync specifications, the *"Nếu id đã tồn tại"* branch MUST be formatted as hierarchical sub-bullets (1 bullet for payload fields present, 1 bullet for omitted fields keeping DB data) with independent Base-36 IDs for each sub-rule.
>     - **Hierarchical Deduplication & Anti-Redundancy Principle (Nguyên tắc Khử Trùng Lặp Phân Cấp & Chống Lặp Từ)**: In hierarchical series `[Phạm vi / Ngữ cảnh] > [Vị trí chi tiết]` (e.g. `Cụm vế > Đầu mỗi`), NEVER repeat the same noun across both sides (prohibited `Cụm nhiều phần > Đầu mỗi phần`, required `Cụm vế > Đầu mỗi` or `Cụm từ > Đầu mỗi phần`).
>     - **Cross-Column Zero-Redundancy in Tables (Nguyên tắc Đơn Nhiệm Cột Bảng & Khử Thừa Chéo)**: Each table column has a single responsibility. Succeeding columns MUST NOT repeat subjects, positions, or prefixes already established in preceding columns. The `GHI CHÚ` column MUST strictly focus on special conditions, delimiters, or exceptions (e.g. `Các vế phân tách bởi (':', '!', '->')`), never repeating redundant phrases like `Trước mỗi...` or `Đầu mỗi...`.
>     - **Concise Technical Lexicon Standard (Quy chuẩn Từ điển Rút gọn Văn phong Kỹ thuật)**: Enforce concise technical phrasing: use `phân tách bởi` instead of `ngăn cách bởi dấu phân tách`, use `đầu mỗi` / `trước từng` instead of `ở vị trí đầu của mỗi`, use `cài & cấu hình` instead of `cài đặt và cấu hình`.
>     - **Sentence Case for Subtitles & Headings (Quy chuẩn Viết hoa Đầu câu cho Dòng Phụ đề hdn)**: Dòng phụ đề xám mờ `hdn` và các nhãn hiển thị nghiệp vụ **BẮT BUỘC** viết hoa chữ cái đầu câu (Sentence Case), toàn bộ các từ còn lại viết thường (trừ danh từ riêng và từ khóa kỹ thuật như `a2u`, `Vault`, `QMD`, `API`, `JSON`). Tuyệt đối cấm viết hoa kiểu Title Case từng từ.
> 18. **MANDATORY ESCAPED PIPE IN MARKDOWN TABLES RULE**: Inside Markdown table cells, any pipe `|` (whether inside Wikilinks `[[File#Heading\|Alias]]`, HTML attributes `title="... &#124; ..."`, code snippets, or descriptive text) MUST ALWAYS BE ESCAPED as `\|` (and in script generation as `\\\|`) or encoded as HTML entity `&#124;`. Never output a raw unescaped pipe `|` anywhere inside a table row, as Markdown parsers will treat it as a column delimiter and split/break the table layout.
